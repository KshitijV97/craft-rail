# Architecture decision records

Write an ADR when a technical decision has meaningful long-term consequences or alternatives worth preserving. Each record includes stable `ADR-NNN`, title, status, date, decision owner, context/forces, decision, alternatives, consequences (positive and negative), and related requirements, diagrams, code, or ADRs.

Statuses are `proposed`, `accepted`, `rejected`, `deprecated`, and `superseded`. Do not silently rewrite an accepted decision. Correct factual errors transparently; when a decision materially changes, create a new ADR and link the superseded record. ADRs record why, not a chronological implementation diary.
