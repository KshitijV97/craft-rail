# Critical review of CraftRail (November 2026)

- **Status:** proposed — findings are verified; remediations are proposals that need owner approval before implementation
- **Reviewed commit:** `e730bf1` (main, 2026-11-09)
- **Scope:** framework model, workflow, templates, validator, feature initializer, agent adapters, CI/release, template distribution, and project governance

This review deliberately looks for weaknesses. CraftRail's documentation is unusually honest about its limits, and several findings below are already disclosed somewhere in `docs/framework/`. Disclosure is not remediation: a limit that is documented on page 14 but silently bypassed in daily use is still a flaw in the product. Each finding records evidence, impact, and a proposed fix sized for a small, dependency-light tool.

## How findings were verified

Claims marked **Reproduced** were demonstrated against a throwaway clone of the reviewed commit. The commands below can be re-run from a clean clone:

```bash
python3 scripts/validate_docs.py            # exit 0, 1 warning
python3 scripts/validate_docs.py --strict   # exit 1 on a clean repository
python3 scripts/new_feature.py "Login"      # creates specs/001-login
sed -i '' 's/Status:\*\* draft/Status:** verified/' specs/001-login/spec.md
python3 scripts/validate_docs.py            # still exit 0 with every template placeholder intact
```

Other findings are **Inspected** (read from source) or **Design** (a structural argument about the model rather than a code defect).

## Summary

The core thesis — keep intent, decisions, and evidence in Git, agent-neutral — is sound. The main problem is that the "guardrails" are almost entirely advisory, and the one piece of automation that exists (the validator) does not check the artifacts that matter most. A team can follow every CraftRail command and end up with a green check, a spec marked `verified`, and no actual requirements. Secondary problems are identifier collisions built into the initializer, framework-maintainer content leaking into adopter repositories, no upgrade path for template users, and the framework not using its own process.

## Findings and remediation

### F-01 — Validator passes a fully placeholder spec marked `verified` (Critical)

**Evidence.** `PLACEHOLDER_RE` in `scripts/validate_docs.py` matches only double-brace tokens, an angle-bracket PLACEHOLDER marker, and a bracketed TODO label. The templates use none of these; they use bracketed prose such as `[role]`, `[The system MUST ...]`, and `[Outcome and signal]`. A spec generated by `new_feature.py`, then edited only to set `Status: verified`, validates with zero errors. Status is checked for spelling only, never for consistency with content or with `verification.md` (which still shows a `planned` row).

**Impact.** The single green signal CraftRail offers is satisfied by an empty document. Agents optimise for passing checks; this one rewards flipping a status string. This directly undermines the "verification before declaring completion" principle.

**Remediation.**

1. Make templates use one machine-detectable placeholder syntax (for example `<PLACEHOLDER: role>`) and have the validator flag any remaining marker in a numbered feature folder.
2. Add status-gated content rules for numbered features:
   - `proposed` or later: no placeholders in `spec.md`; at least one requirement and one acceptance criterion declared.
   - `approved` or later: approval metadata present (see F-05); no open rows in the questions table marked blocking.
   - `in-progress`: `plan.md` and `tasks.md` contain no placeholders.
   - `verified`: every acceptance criterion in `spec.md` appears in `verification.md`, and every row is `verified`, `waived` (with owner), or `deprecated`.
3. Add regression tests that generate a feature with the real templates (not stubs) and assert that it fails validation at each status above `draft`.

### F-02 — Adopter's canonical requirements are exempt from validation (Critical)

**Evidence.** `is_exempt()` skips `docs/project/` entirely for placeholder, short-ID, and duplicate-ID checks. Appending a double-brace TODO marker and a two-digit ID to `docs/project/product-brief.md` produces no error. The exemption exists because the starter content is illustrative, but after adoption `docs/project/` is where the project's real business rules and requirements live.

**Impact.** The most important, longest-lived artifacts get the least checking. The exemption silently persists forever after the starter content is replaced.

**Remediation.** Replace path-based exemption with explicit marking. Starter files carry a front-matter flag (for example `craftrail: example`) or live under a clearly named `examples/` tree. The validator exempts only flagged files and emits a warning listing them, so an adopter sees "3 starter files still present" until they are replaced. Keep `templates/` exempt by path, since templates are never canonical content.

### F-03 — No traceability checks (High)

**Evidence.** Duplicate detection is per file (`check_ids` resets `seen` per document). Declaring the same functional requirement ID in `docs/project/requirements/` and in a feature spec passes. References to undeclared IDs (a nonexistent ADR or acceptance criterion mentioned in a plan) pass. `docs/framework/concepts.md` discloses this, but traceability is one of the framework's three headline value propositions.

**Impact.** The "Requirement → AC → Verification" chain is documented but unverifiable. Renumbering or deleting an ID silently orphans references.

**Remediation.** Build an in-memory ID graph, still standard-library only:

1. Collect declarations (list-item and first-cell table forms already recognised) with their file and scope.
2. Define uniqueness scopes from `concepts.md` as config: project-wide for business, functional, non-functional, constraint, and ADR IDs; feature-local for acceptance criteria, tasks, and tests.
3. Report duplicates within a scope, and references to IDs with no declaration in scope (error for ADR/requirement references, warning for others initially).
4. Report acceptance criteria in a `verified` spec with no verification row (ties into F-01).
5. Optionally emit `--report trace` as Markdown or JSON so reviewers can see the matrix without trusting a percentage.

### F-04 — Initializer stamps the feature number into requirement IDs (High)

**Evidence.** `create_feature()` replaces every `NNN` with the feature number. Templates use `NNN` both for the feature number and for requirement IDs. Feature 001 is therefore created with functional, non-functional, constraint, business-rule, and acceptance-criterion IDs all numbered 001 — the same IDs as the starter project register and the example feature. Feature 004 gets requirement 004, and so on. The unit test `test_creates_from_templates_with_metadata` asserts this behavior as correct.

**Impact.** Every new feature starts with IDs that collide with the project register, conflate "feature number" with "requirement number", and teach adopters an incorrect scheme. Combined with F-03, nothing catches it.

**Remediation.** Use distinct tokens: `{feature}` for the feature number and a separate requirement placeholder that the validator flags (F-01). Either leave requirement IDs for the author to allocate, or have the initializer allocate the next free project-wide ID from the F-03 graph. Fix the test to assert the new behavior.

### F-05 — Approval is an editable string (High)

**Evidence.** `Status: approved` is free text. There is no `Approved by` or `Approved on` field in the spec template, no CODEOWNERS file, and no check that a status change was reviewed by an authorised person. The docs correctly state that status "does not grant an agent authority", but nothing prevents an agent from writing it, and AGENTS.md's "Draft or proposed specifications are not implementation approval" can be satisfied by editing one word.

**Impact.** The human-approval boundary — the framework's central safety claim — depends entirely on agent compliance and reviewer attention.

**Remediation.**

1. Add `Approved by` (person or role) and `Approved on` metadata to the spec and ADR templates; the validator requires them for `approved` and later.
2. Ship a starter `.github/CODEOWNERS` covering `specs/*/spec.md`, `docs/project/requirements/`, and `docs/project/decisions/`, with docs explaining branch protection "require review from code owners".
3. Optional CI check (provider-neutral script, run by any CI): if a diff changes a spec's status to `approved` or later, the commit author must not be the only approver recorded, and the PR must carry a human approval. Document the GitHub implementation as one adapter.
4. Add an explicit AGENTS.md rule: agents must never change a status to `approved`, `verified`, or `waived`, or edit approval metadata.

### F-06 — Guardrails are advisory; nothing links code to specs (High)

**Evidence.** The PR template asks about documentation impact but not which spec or requirement IDs a change implements. No check detects code changes without a spec reference, or spec drift after code changes. "Converge" relies entirely on discipline.

**Impact.** The tagline promises guardrails; the product delivers conventions. Documentation drift — the failure mode CraftRail exists to prevent — is not detected.

**Remediation.**

1. PR template: add a required "Implements" field (feature path and IDs) or an explicit "No spec: reason" escape (typo, refactor, emergency).
2. Provide an optional `scripts/check_change.py` that, given a base ref, fails when configured source paths change without a spec reference in the PR body or commit trailers (for example `Refs: specs/012-login`), and warns when a feature's code changed but its `verification.md` did not.
3. Rename or qualify the positioning ("conventions and checks for agent-driven development") until enforcement exists, so the claim matches the product.

### F-07 — Template ships framework-maintainer content (High)

**Evidence.** A repository created via "Use this template" receives CraftRail's own `AGENTS.md` (titled "CraftRail repository instructions", including framework-development rules like "Do not add provider-specific dependencies… to core artifacts, templates, validation"), `CHANGELOG.md`, `ROADMAP.md` (including the Golden Tide Retreat Vercel debt), the Codex build brief and start prompt, `vercel.json`, `zensical.toml`, the docs-site stylesheet, release workflows, and a license with unfilled copyright fields. `REQUIRED_PATHS` makes `vercel.json`, `zensical.toml`, `ROADMAP.md`, `CODE_OF_CONDUCT.md`, the release workflow, and others mandatory, so deleting them breaks validation.

**Impact.** Adopters must manually separate framework from project, and the always-loaded agent instructions describe the wrong project. An agent in an adopter repo will apply CraftRail's maintainer policy to unrelated code.

**Remediation.**

1. Split into two trees: the framework repository (this one) and a `starter/` (or separate template repository) containing only adopter files: a generic `AGENTS.md`, `CLAUDE.md`, `docs/project/`, `specs/`, `templates/`, `scripts/`, and a minimal CI job.
2. Write the adopter `AGENTS.md` as project-neutral ("This project uses CraftRail…") and keep framework-maintainer rules in a separate file that is not shipped.
3. Move `REQUIRED_PATHS` into a config file (`craftrail.toml` or JSON, read with `tomllib`/`json`) with a minimal default: `AGENTS.md`, `specs/`, `templates/feature/`.
4. Move the build brief and start prompt to `docs/history/` or remove them (D-007 already permits this).

### F-08 — No upgrade path for template-derived repositories (High)

**Evidence.** GitHub templates copy files without history. There is no framework version marker in adopter repos, no changelog of template/validator changes aimed at adopters, and no update mechanism. A bug fix to the validator (such as F-01) cannot reach existing adopters except by manual copying.

**Impact.** Every adopter forks the framework permanently at the version they started with. Fixes from this review will not reach them.

**Remediation.** Record the framework version in the adopter config (`craftrail_version = "0.x"`). Publish versioned release assets containing `scripts/` and `templates/`, and document a one-command update (`curl`/`git archive` into place, or a small `scripts/update_framework.py` that fetches a pinned tag and shows a diff). Keep adopter-owned files (`docs/project/`, `specs/`) out of the update set by construction. Maintain an "Adopter impact" section in CHANGELOG.

### F-09 — `--strict` can never pass (Medium)

**Evidence.** `validate()` always appends the OpenAPI warning, even when `openapi.yaml` does not exist. On a clean repository, `--strict` exits 1. The validation guide documents this.

**Impact.** A strict mode that always fails is unusable as a CI gate, so teams will never enable it, and future useful warnings will be ignored.

**Remediation.** Emit the warning only when an OpenAPI file exists, make it suppressible via config (`acknowledged_limits = ["openapi"]`), or downgrade it to an informational line not counted as a warning. Add a test that a clean repository passes `--strict`.

### F-10 — Validator scans virtualenvs and dependencies (Medium)

**Evidence.** `markdown_files()`, `mermaid_files()`, and the JSON scan use `rglob` with only `.git` excluded (the JSON scan does not exclude even `.git`). A broken README in `.venv/` and an invalid `package.json` in `node_modules/` both produce errors. `docs/implementation/index.md` tells contributors to create `.venv-dev`, which is not in `.gitignore`, so following the docs both risks committing a virtualenv and feeds third-party files to the validator.

**Impact.** False failures in any real project with dependencies; slow runs on large repos; erosion of trust in the tool.

**Remediation.** Enumerate files via `git ls-files` when inside a Git work tree (falling back to `rglob` with a default exclude list: `.venv*`, `venv`, `node_modules`, `site`, `dist`, `build`, `.tox`, caches). Support `exclude` globs in config. Add `.venv-dev/` (or `.venv*/`) to `.gitignore`.

### F-11 — Feature numbers collide across parallel branches (Medium)

**Evidence.** `next_feature_number()` uses the local maximum. Two branches each running `new_feature.py` produce `001-a` and `001-b`; both survive the merge without conflict.

**Impact.** Feature IDs are meant to be stable references; collisions make "feature 001" ambiguous in PRs, commits, and traceability.

**Remediation.** Have the validator reject duplicate numeric prefixes under `specs/`. Offer `--number` to set an explicit number, and document either allocating numbers at merge time or using an issue-number scheme (`specs/gh-142-login`). Make the prefix pattern configurable.

### F-12 — Workflow scaling relies on agent self-classification (Medium)

**Evidence.** AGENTS.md says "Scale the process to the task: for a small fix… without creating unnecessary specification files". The scaling table in `workflow.md` is explicitly "guidance, not a complexity score". The party deciding whether a change is "small" is the agent that benefits from skipping steps.

**Impact.** The cheapest path is always available. Without an objective trigger, high-risk changes can be classified as small fixes.

**Remediation.** Define objective escalation triggers in AGENTS.md (configurable per project): changes touching auth, permissions, money, persistent schema or migrations, public contracts (`docs/project/contracts/`), or files listed in a `high_risk_paths` config always require an approved spec. Require the agent to state its classification and the trigger check in its report. F-06's change check can enforce the path-based part.

### F-13 — Agent adherence is untested (Medium)

**Evidence.** `agent-compatibility.md` shows the portability acceptance table as all `pending`. No test checks whether any agent actually follows AGENTS.md (for example, refuses to implement a `draft` spec).

**Impact.** The framework's effectiveness rests on an unmeasured assumption about agent behavior.

**Remediation.** Run and record the existing portability procedure (ROADMAP item 1). Add a small scenario suite under `docs/evals/` — plain-language task prompts plus expected observable behavior (for example: "implement spec 900, which is draft" → agent stops and asks; "fix a typo" → no spec created; "add a column to the users table" → agent requires a spec). Record results per agent/version/date. This stays provider-neutral because scenarios are prose and outcomes are judged by a human.

### F-14 — CraftRail does not dogfood its own process (Medium)

**Evidence.** The repository has no numbered feature specs for its own capabilities, no ADRs (`docs/project/decisions/` holds only a README; decisions live in an ad hoc `D-` table in `assumptions-and-decisions.md`), and `docs/project/` contains fictional starter content rather than CraftRail's requirements. The validator and initializer have no requirement IDs that their tests trace to.

**Impact.** Credibility, and lost feedback: the defects in F-01, F-04, and F-11 would have surfaced immediately had the framework been used to build itself.

**Remediation.** After F-07's split, give the framework repo its own `docs/project/` (CraftRail's requirements), convert D-001 through D-009 into ADRs, and specify this review's remediations as numbered features (for example "validator traceability graph", "starter split"). Link unit tests to requirement IDs in their docstrings.

### F-15 — Status vocabularies are mostly unvalidated (Medium)

**Evidence.** Only feature spec status is checked. Verification row statuses, task statuses, ADR statuses, plan status (the plan template has a `Status` field with no defined vocabulary), and project register statuses are unchecked. The example spec's status line is `verified (illustrative only…)`, which the validator's own regex would reject if the example were not exempt.

**Remediation.** Validate each vocabulary from `concepts.md` in its table column or metadata line; define the plan status vocabulary or remove the field; fix the example to use a clean status plus a separate note line.

### F-16 — Markdown parsing shortcuts (Low)

**Evidence.** `check_fences()` treats any same-character fence line, including one with an info string, as a closer; CommonMark requires a closer to have no info string and to be at least as long as the opener. `without_fences()` uses a different rule (exact back-reference), so the two functions can disagree about where code ends. Links containing parentheses are truncated; reference-style links and heading anchors are unchecked; links resolving outside the repository root are accepted if the target exists on the author's machine. Inline code spans are not excluded from placeholder and ID checks, so documentation that merely names the placeholder syntax in backticks fails validation (this review hit that error while being written).

**Remediation.** Unify fence handling into one line-based scanner that follows the CommonMark opener/closer rules and returns fenced line ranges used by every check, and strip inline code spans before placeholder and short-ID checks. Reject link targets that resolve outside the repository root. Add anchor checking using GitHub-style slug generation for headings (standard library is sufficient).

### F-17 — Documentation duplication and hard-coded facts (Low)

**Evidence.** The three-layer model, the "framework owns the process" principle, the lifecycle, and the agent-adapter explanation are restated in README, `overview.md`, `design-rationale.md`, `agent-compatibility.md`, `github-template-usage.md`, and AGENTS.md. Pages hard-code facts that will rot: "run 26 unit tests", "reviewed 2026-11-08", pinned tool versions, deployment state.

**Impact.** A framework whose purpose is preventing documentation drift has a high internal drift surface; every policy change must be repeated in five places.

**Remediation.** Designate one canonical page per concept and replace restatements with a one-line summary plus link. Remove counts that tests can change. Put review dates in one table (`assumptions-and-decisions.md`) and have the validator warn when a recorded review date is older than a configurable age.

### F-18 — Supply-chain and CI hardening gaps (Low)

**Evidence.** Actions are pinned to mutable major tags (`actions/checkout@v4`), not commit SHAs. `release.yml` grants `contents: write` at workflow level, so the quality job (which installs third-party packages and runs pre-commit hooks) holds a write token. `requirements-docs.txt` pins a 0.1.0 beta generator. `vercel.json` installs packages without hash checking.

**Remediation.** Pin actions by SHA with a comment naming the version, and add Dependabot/Renovate for updates. Move `contents: write` to the `release` job only and set workflow-level permissions to `contents: read`. Use `pip install --require-hashes` with hashed requirement files for CI and docs builds.

### F-19 — Unresolved release blockers (Governance)

**Evidence.** LICENSE is marked "provisional draft" with an unfilled copyright line, yet the repository is public and marked as a template, so adopters copy an unclear license. The brand conflict with Craftrail Inc. is recorded as a release blocker but promotion has begun (public template, hosted docs). The docs site lives under an unrelated Vercel scope behind authentication (TD-001), while README links to it as the primary documentation.

**Remediation.** Resolve the license (owner decision) before further promotion and fill the copyright holder; until then, state clearly in README that terms are provisional. Make a recorded brand decision. Either make the docs site public or point README at the in-repo `docs/adoption/` as primary. These are owner decisions; no change here should be made without them.

## Proposed remediation order

The order front-loads fixes that make the existing green signal truthful, then fixes the distribution model before more adopters fork a flawed version.

| Phase | Findings | Outcome | Size |
|---|---|---|---|
| 1. Make the check honest | F-01, F-02, F-04, F-09, F-10 | A placeholder or colliding spec fails; strict mode is usable; no false positives from dependencies | Small–medium; validator, templates, tests |
| 2. Make approval and traceability real | F-03, F-05, F-11, F-15 | ID graph, approval metadata, CODEOWNERS starter, status rules | Medium |
| 3. Fix distribution | F-07, F-08, F-19 | Clean starter, config file, versioned updates, license decided | Medium; needs owner decisions |
| 4. Add enforcement and evidence | F-06, F-12, F-13 | Change-to-spec check, objective escalation triggers, recorded agent evals | Medium |
| 5. Dogfood and tidy | F-14, F-16, F-17, F-18 | Framework built with its own process; parser and CI hardening | Ongoing |

Phases 1 and 2 add no third-party dependencies and keep the validator standard-library only, consistent with D-005. Introducing a config file (`tomllib`) requires Python 3.11+ or a JSON config to keep 3.10 support; that choice should be recorded as an ADR.

## Owner decisions needed

1. Approve this review's remediation scope and order, or select a subset.
2. Starter split (F-07): separate template repository, or a `starter/` subtree in this one.
3. Config format and Python floor (JSON for 3.10, or TOML with 3.11+).
4. Positioning (F-06): keep "guardrails" and build enforcement, or soften the claim now.
5. Release blockers in F-19: license, brand, docs hosting visibility.

## Limitations of this review

Agent behavior was not tested in Codex, Claude Code, or OpenCode; F-13 is therefore an absence of evidence rather than a demonstrated failure. The documentation site build and Vercel deployment were not exercised. Severity ratings are the reviewer's judgment about impact on adopters, not measured incident data.
